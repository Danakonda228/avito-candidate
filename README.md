# Avito 

Для каждого поискового запроса выбираю из корпуса (189k объявлений) 50 кандидатов, метрика Recall@50.

| | CV recall@50 | CV weighted* | LB |
|---|---|---|---|
| BM25 по всем полям | 0.377 | | |
| эвристика (текст x локация x микрокатегория x фильтры) | 0.881 | 0.875 | 0.826 |
| ранкер W (все фичи) | 0.937 | 0.931 | 0.872 |
| ранкер B (без истории и качества) | 0.925 | | 0.874 |
| ансамбль W + B (итог) | 0.935 | | 0.878 |
| покрытие пула (потолок) | 0.975 | 0.972 | |

\* доли запросов с фильтрами и без приведены к составу теста (34/66)

## Запуск

Python 3.11+. Финальный прогон: Python 3.14, Windows 11.

pip install -r requirements.txt

Положить `train.parquet`, `benchmark_queries.parquet`, `benchmark_items.parquet` в `data/` и выполнить `solution.ipynb` целиком. Ноутбук считает CV, обучает финальную модель и пишет `answer.csv`. Около 25 минут, пик памяти около 6 ГБ.

Сид фиксирован, поэтому на версиях из `requirements.txt` результат повторяется; md5 файла выводится в последней ячейке. На другой версии Python или стеммера кандидаты могут слегка отличаться (CV меняется в 4-м знаке). На Windows `to_csv` пишет переводы строк `\r\n`, поэтому md5 зависит ещё и от ОС.

## Валидация

Одна группа по `(search_query, search_location_id, search_infm_params_text, search_category, search_is_delivery_search)` считается одним запросом, а все выбранные в ней `item_id` составляют таргет. Recall можно честно посчитать только для групп, у которых все выбранные объявления есть в корпусе.

Случайный сплит не годится. В нём 82% отложенных запросов уже встречались в истории, а в тесте таких только 36%. Кроме того, тестовые запросы длиннее (3.2 слова против 2.3 в train) и реже идут с фильтрами. Поэтому валидацию я собрал так:

1. тексты запросов сэмплирую равномерно, а не пропорционально частоте;
2. для 64% выбранных текстов удаляю из истории все строки с этим текстом. После этого знакомых запросов в val 29%, в тесте 31%;
3. `val` (3000 запросов) идёт на оценку, `rk` (5000) на обучение ранкера. Все статистики считаются только по оставшейся истории, чтобы не было утечки.

## Кандидаты

Для каждого запроса по всему корпусу считаются такие скоры:

1. `bm25_title / params / desc / all`: BM25 по стемам (Snowball). В `all` склеены заголовок x3, параметры и описание;
2. `char_title`: tf-idf по символьным 3–5-граммам заголовка, ловит опечатки и формы слов;
3. `hist_text`: BM25 по текстам запросов, по которым это объявление выбирали в train;
4. `knn_item`: объявления, которые выбирали по 30 ближайшим запросам train (word + char tf-idf);
5. `exp_title / exp_all`: query expansion. Беру tf-idf заголовков всех объявлений, выбранных по ближайшим запросам, включая объявления не из корпуса. Так «сауна» находит «баню»;
6. `p_mc`: распределение микрокатегорий по ближайшим запросам;
7. `p_loc`: `P(item_loc | search_loc)` по train. Поиск по области ведёт в города области;
8. `dist`: расстояние в км от точки локации поиска до объявления. Координаты локации считаю как медиану координат объявлений в ней;
9. `filt`: доля фильтров поиска («Вид услуги ...», «Тип услуги ...»), которые есть в параметрах объявления. Фильтры выполняются в 97% случаев, поэтому это множитель, а не отсечение.

Эвристика собирает их так:

combo = text * (0.05 + p_loc + 0.2 * exp(-dist / 15)) ** 0.5 * (0.05 + p_mc) ** 0.3 * (0.1 + filt)

где `text` — сумма нормированных текстовых скоров. Пул кандидатов состоит из top-300 по `combo` и top-50 по каждому отдельному скору, в среднем около 490 объявлений на запрос.

## Ранкер

`HistGradientBoostingClassifier` (300 итераций, lr 0.05, 63 листа). Обучается на все позитивы плюс 150 случайных негативов на запрос. Всего 44 фичи: сами скоры, их нормировка на максимум по запросу, ранги внутри пула, популярность объявления в истории, рейтинг, отзывы, цена, флаги, совпадение локации, длина запроса, число фильтров.

Для сабмита ранкер переобучается на `rk + val`, а статистики истории пересчитываются по всему train.

Permutation importance по группам фич (падение CV):

| группа | Δ recall |
|---|---|
| distance | -0.036 |
| text | -0.035 |
| location stats | -0.012 |
| history | -0.011 |
| query expansion | -0.003 (основной вклад идёт через пул) |

## CV vs LB и ансамбль

Первый сабмит ранкера W дал на платформе 0.872 при CV 0.937. Чтобы понять разрыв, отправил диагностические варианты (таблица выше, плюс «холодный» ранкер со всеми фичами: LB 0.706).

«Холодная» история: из истории убраны все строки с объявлениями из `val` и `rk`, как будто это новые объявления.

1. Разрыв CV/LB ~6 п.п. одинаковый у эвристики и у ранкера. Значит, модель не переобучена, тест просто сложнее валидации. Скорее всего в тесте у запросов чаще несколько правильных объявлений, а валидация из-за отбора (все выбранные объявления должны быть в корпусе) почти целиком из запросов с одним ответом.
2. «Холодный» ранкер со всеми фичами учится занижать объявления с историей и проваливается до 0.706. Значит, в тесте много объявлений, которые уже встречались в train, и история нужна.
3. Модель B не смотрит на историю и качество объявления, но даёт тот же LB, что и W, при заметно другой выдаче (пересечение top-50 ~86%).

Итоговый ответ — ансамбль W и B (LB 0.878, лучший из всех сабмитов): среднее геометрическое их рангов внутри пула. На обычной валидации 0.935 (W 0.937, B 0.925), на «холодной» 0.925 (W 0.921, B 0.923): ансамбль почти не уступает лучшей модели в обоих сценариях.

## Ошибки

1. Объявления без истории в train дают recall 0.90, объявления с историей 0.98. Это основной остаток ошибок.
2. Разрыв в словах: «сауна» против «Русская баня на дровах», «вынести диван» против «Вывоз старой мебели».
3. Общие запросы в больших городах («сантехник»): подходящих объявлений сотни, и выбор пользователя почти случаен.
4. Соседние населённые пункты без статистики по паре локаций. Эту проблему закрыл признак `dist`, до него `p_loc = 0` отсекал такие объявления.

## Что не зашло

- hard negatives (top по эвристике) вместо случайных: 0.9360 против 0.9362
- 300 негативов на запрос или все негативы: 0.9352
- модель побольше (600 итераций, lr 0.03, 127 листьев): 0.9316
- вес query expansion 2.0 в эвристике вместо 1.0: 0.8816 против 0.8866
